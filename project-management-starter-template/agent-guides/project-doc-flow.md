# Project Doc Flow

本指南用于帮助 Agent 撰写正式开发文档。它的核心不是“把文档放到哪里”，而是结合项目语境与行业专业标准，写出可执行、可验收、可追溯的高质量开发文档。

## 适用范围

- 新功能开发文档
- 优化 / 重构开发文档
- bugfix 根因与修复文档
- 工具能力 / 数据流水线 / Agent 工作流文档
- UI / UX / 游戏机制 / 安全 / 可靠性相关开发文档

## 工作步骤

1. 判断任务是否已经挂靠某个版本 / Phase / Issue / Backlog。
2. 已挂靠时，优先读取对应版本入口、Phase、subplan、执行纪律、相关 Specs / Issue / QA。
3. 未挂靠时，从 `ProjectManager/Overview.md`、`ProjectManager/Plan/README.md`、`ProjectManager/Specs/_index.md` 开始确认归属。
4. 识别需求类型，并选择对应专业标准：应用开发、游戏开发、数据处理、Agent 工具、UI/UX、安全、可靠性等。
5. 写文档前通过质量门：架构影响、数据/状态影响、失败路径、备选方案、验收方式、QA 映射、current spec 影响。
6. 再决定落点：版本 subplan、Specs dated doc、Specs current、Reports 或 QA。

## 通用质量门

| 质量门 | 必须回答的问题 |
|---|---|
| 需求来源 | 关键需求是否能追溯到用户、Plan、Spec、Issue、Backlog、诊断或外部标准 |
| 目标与非目标 | 做什么、不做什么、为什么现在做 |
| 实现架构 | 模块归属、依赖方向、公共接口、兼容策略 |
| 数据 / 状态 | 是否影响持久化、迁移、同步、缓存、索引或日志 |
| 失败路径 | 输入异常、外部依赖失败、权限不足、质量不足时如何处理 |
| 备选方案 | 至少记录选定方案和一个未采用方案，说明后果 |
| 可验证性 | 每个关键需求对应测试、QA、人工核验或产物验收 |
| 长期规格 | 是否影响 `Specs/<feature-slug>/current.md` |

## 项目适配位

新项目应补充：项目类型、主要行业标准、关键风险、正式开发文档分类、默认 QA 深度、常用证据格式。
